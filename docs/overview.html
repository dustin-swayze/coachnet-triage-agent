The Partner Sync Triage Agent is a read-only AI agent that answers the question "why didn't this case sync?" for TrxNow's partner integrations. A partner's HubSpot instance syncs with TrxNow's Salesforce org through a MuleSoft application running on Anypoint CloudHub 2.0. When someone reports a problem with a case, the agent checks the Mule application's health, reads the case from Salesforce, finds the matching transaction in the Mule logs, matches the evidence against a runbook of known failure modes, and replies with a diagnosis, the evidence it used, a suggested fix, and a confidence score.

The first partner is Coach Net. The code is partner-generic: partner identity comes from configuration, so a second partner is a second configuration file rather than a fork. The project is also a learning exercise in agent design (agent loops, tool design, retrieval-augmented generation, evaluation) and a pitch to TrxNow's integration leadership, so its code and documentation are written to demonstration quality.

As of the end of Session 1 the agent runs end to end in mock mode, against synthetic data and a scripted stand-in for the language model, at zero cost and with no API key. Live integrations are planned for the work laptop in Phases 2 to 4.

Background

Before this project, verifying a report such as "Case 00412345 didn't sync" meant moving between Anypoint Runtime Manager, the Mule logs, and Salesforce. That was slow at a desk and close to impossible from a phone, and there was no quick way to learn that the Mule application itself was down. The agent compresses that investigation into one plain-English question with an auditable answer in about 30 seconds.

Five failure modes account for most real sync problems, as described by the integration owner. Each became a runbook entry and a mock scenario:

  • A case is duplicated without the redispatch flag.
  • A case appears sent but never reaches TrxNow's Priority Queue.
  • A send fails because the inbound HubSpot payload does not match the API contract.
  • A case fails in the DataWeave transform.
  • Everything else: expired credentials, HubSpot rate limits, and the Mule application being down or restarting.

Design principles

Nine constraints were fixed before any code was written. They are copied into every handoff document.

#ConstraintHow it is enforced
1Read-onlyNo tool interface can express a write. Fixes that need writes are suggestions for a human.
2Fail-closed scopingThe partner filter is built into every query and rechecked on the result. A tool that cannot prove scope raises an error.
3No real TrxNow data in the repoSynthetic fixtures only, audited by a separate agent. Secrets live only in a gitignored .env.
4Least-privilege credentialsOne read-only credential per integration, proven read-only in the sandbox before each phase goes live.
5Bounded agentStep cap, per-tool timeout and total time budget, all held in graph state. Hitting one returns partial results marked incomplete.
6Every tool call tracedOne redacted JSONL line per tool call, node and model call, in one file per run.
7Swappable LLM providerinit_chat_model reads provider and model from configuration.
8Portable to AgentforceTools are plain typed functions with Pydantic schemas, separate from the LangGraph orchestration.
9Zero cost in mock modeA scripted chat model and local embeddings run the whole graph with no key.

One further principle runs through the design: deterministic where possible, LLM only where judgment is needed. The health check, routing, limits, scoping, guards and final rendering are plain code. The model extracts the request and interprets the evidence.

Architecture

Control flow

The agent is an explicit LangGraph StateGraph. LangChain's prebuilt agent was rejected because it lets the model decide whether to check health at all. In the graph, the health check is structurally first.

Figure 1. The triage graph. Every edge leaving a node is either fixed or chosen by a small routing function in code.

State

Graph state is a typed dictionary whose values are Pydantic models, so every piece of evidence is validated and serializable. Lists of evidence, errors, runbook hits and messages use append reducers so nodes add to them without overwriting. Limits live in state too: steps_used, step_cap, deadline, incomplete and incomplete_reason. That lets the final node report "incomplete" with everything found so far instead of the run raising an exception.

Limits and failure handling

Every tool call passes through one function that checks the step cap and the run deadline, runs the tool in a worker thread with a timeout, writes a trace line, and turns any tool error into a recorded error plus a line of evidence. A failed lookup is evidence, such as "no CNET case found for 00499999", rather than a crash. Model calls go through a matching function under the same deadline.

ErrorMeaningEffect on the run
ScopeErrorScoping to the configured partner could not be provenRecorded; no data returned
NotFoundErrorNo record or no log lines matchedRecorded as evidence; run continues
UpstreamErrorThe remote API failed (status, short redacted body, retryable flag)Recorded; run continues
ToolTimeoutErrorThe per-tool timeout or remaining run budget was exceededRecorded; run continues or ends incomplete

Defaults: 8 tool calls per run, 15 seconds per tool, 60 seconds per run. LangGraph's own recursion limit is set well above the step cap as a backstop that should never fire.

Safety mechanisms

  • Identifier guard. A case number, ticket id or correlation id the model extracts must appear verbatim in the user's text. Invented ids are dropped and logged, and real ids the model missed are recovered by regular expression.
  • Runbook-citation guard. The diagnosis may cite only runbook entries retrieved in the same run. Unknown ids are dropped and confidence is capped at 50%.
  • Evidence-based confidence cap. With no case and no log transaction, confidence is capped at 40%.
  • No-evidence route. When neither the case nor any logs are found, the graph skips diagnosis and reports what it looked up and what failed.
  • Untrusted-data framing. The user's text, case fields, log lines and tool results reach the model inside tagged data blocks, with an instruction to treat them as data. A closing tag smuggled into the data is neutralized. A deliberate prompt-injection string sits in the fixtures to keep this honest.
  • Redaction everywhere data leaves code. Keys and values that look like secrets, tokens, JWTs or personal data are masked before they are written to a trace, placed in a prompt, or uploaded to LangSmith.

Observability

Two layers, by design (ADR 0006):

  • JSONL traces are always on and are the system of record. Each run writes traces/<run_id>.jsonl with events for run start and end, node entry and exit, tool calls, model calls with token usage, limit hits and guard actions. They never leave the machine.
  • LangSmith is optional and off by default behind LANGSMITH_ENABLED. When on, a run appears as one nested trace with every tool and model call, tagged with the same run id as its JSONL file. Uploads pass through the same redaction. When off, tracing is forced off even if a stray LANGSMITH_TRACING variable is set.

Command-line interface

All commands run from the repository root in Git Bash.

uv run python -m triage chat     # interactive; :app <state> switches mock app health, :quit exits
uv run python -m triage ask "Case 00412345 looks like a duplicate, what happened?"
uv run python -m triage index    # rebuild the runbook index from docs/runbook
uv run python -m triage health   # one-shot app health check; exit code 0 healthy, 1 unhealthy, 3 unknown
uv run python -m triage slack    # Slack bot and health-alert poller (Socket Mode); setup in docs/slack-setup.md

Slack bot

The Slack bot brings the agent to a phone. It is a thin layer over the same run function as the CLI, so it uses the same graph, tools, limits, guards and traces. It connects out to Slack over Socket Mode, so it needs no public web address. It currently runs in mock mode in a personal demo workspace (ADR 0007).

FeatureBehaviour
Ways to ask/triage case 00412345 ..., an @mention in an approved channel, or a direct message
Reply flowAcknowledges within Slack's 3 seconds, posts "Looking into it", replaces it with the answer, and puts the evidence in the thread
AccessFail-closed, by where the answer lands: only allowlisted channels, or DMs with allowlisted users. Empty allowlists refuse everyone. Refusals are private and never run the agent.
Abuse limitsOne run in flight per user, 20 per user per hour, at most 4 at once
EscapingAll user, case, log and model text is escaped, so it cannot ping @channel or create links
Health alertsA poller posts once when the app goes unhealthy, once on recovery with the outage length, and once if the status check fails three times in a row
Demo switch/triage :app down and :app healthy change the simulated app health, in mock mode only
Scopesapp_mentions:read, chat:write, commands, im:history. It cannot read channel history.
AuditEach run's local trace records that it came from Slack and the requester's Slack user id

Moving it to TrxNow's Slack needs workspace-admin approval for a separate app, approval for case details in Slack, and an always-on host on Azure.

Claude Code skills and memory

Project knowledge lives in the repository rather than in any chat session: CLAUDE.md for Claude Code, HANDOFF.md for the next session, plus the roadmap, glossary and decision records. Limitations

  • Mock-mode tests prove routing, tool contracts, scoping, limits, tracing and retrieval. The model's replies in mock mode are scripted, so they do not show that a real model reasons well. Phase 5 evals measure that.
  • Live mode has never run. The live tool modules are stubs, and Salesforce field names are placeholders.
  • Retrieval in mock mode is lexical. It works for error codes and the seven entries; semantic embeddings may be needed as the runbook grows.
  • A timed-out tool keeps running in its worker thread until it returns, because Python cannot stop a thread. Live tools must set HTTP-level timeouts.
